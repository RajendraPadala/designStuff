# 1. Java Threads: Evolution, Internals & Performance

## 1.1 Pre-Java 8 Threading Model

### The Primitive Era (Java 1.0–1.4)
Java threads were **1:1 mapped to OS kernel threads**. Every `new Thread()` triggered an OS-level thread creation — a heavy operation involving:
- **Kernel space allocation** for the Thread Control Block (TCB)
- **Stack allocation** (default ~1MB on 64-bit JVM, `-Xss` tunable)
- **Context switch penalty**: ~1–10 microseconds of kernel overhead

**Green Threads** (Java 1.1 on Solaris only) were an early attempt at M:N threading where the JVM managed user-space threads. They were abandoned due to poor SMP scaling — a single green thread blocking on I/O would block all threads in that process.

### The Executor Framework (Java 5)
Java 5 introduced `java.util.concurrent` with:
- **`ThreadPoolExecutor`**: Core pool size, max pool size, work queue (bounded/unbounded), rejection policies
- **`Future<T>`**: A placeholder for async results, but **blocking** via `get()`
- **`Callable<T>`**: Returns values and throws checked exceptions

**Synchronization primitives:**
- `synchronized` keyword: Monitor-based locking with object header mark words
- `ReentrantLock`: CAS-based AQS (AbstractQueuedSynchronizer) locks with fairness options
- `volatile`: Memory visibility guarantee via StoreLoad barriers, but no atomicity

**Performance characteristics pre-Java 8:**
- **Thread creation cost**: ~1ms + memory overhead
- **Context switching**: Expensive; minimizing threads was critical
- **Lock contention**: `synchronized` had biased locking (until Java 15 when it was removed) and thin/thick lock inflation
- **No composition**: You couldn't chain async operations without nested callbacks or blocking waits

## 1.2 Java 8+ Threading Revolution

### ForkJoinPool & Work-Stealing (Java 7 stabilized, Java 8 mainstreamed)
`ForkJoinPool` is the engine behind Java 8's parallel features. It introduced **work-stealing**:

> "Each worker thread maintains its own double-ended queue (deque) of tasks. When a thread finishes its tasks, it steals from the **tail (FIFO)** of another thread's deque, while the owner processes from the **head (LIFO)**." 

**Key internals:**
- **LIFO for owner**: Improves cache locality (recently forked tasks likely share cache lines)
- **FIFO for stealers**: Reduces contention and often steals larger, older tasks suitable for further splitting
- **Common pool**: `ForkJoinPool.commonPool()` uses `availableProcessors() - 1` threads 

### CompletableFuture (Java 8)
`CompletableFuture` solved `Future`'s limitations:
- **Non-blocking composition**: `thenApply`, `thenCompose`, `thenCombine`
- **Exception handling**: `exceptionally`, `handle`
- **Explicit completion**: `complete(T)`, `completeExceptionally(e)`
- **Default executor**: Uses `ForkJoinPool.commonPool()` unless specified 

**Performance impact:**
- Eliminates blocking `get()` calls
- Enables **pipeline parallelism** where stage N starts as soon as stage N-1 emits a result
- Risk: Chaining many stages on `commonPool` can starve other parallel streams

# 2. Java Collections: Evolution & Internals

## 2.1 Pre-Java 8 Collections

### HashMap (Pre-Java 8)
- **Structure**: Array of buckets + linked lists for collision resolution
- **Hash function**: `hashCode()` → bitwise operations
- **Collision handling**: Separate chaining with linked lists
- **Worst-case get/put**: **O(n)** when all keys collide (hash collision attack vulnerability)

### ConcurrentHashMap (Pre-Java 8)
- **Segment-based locking**: 16 segments by default (concurrency level)
- Each segment was a mini-HashMap with its own lock
- **Tradeoff**: Better than `Hashtable` (single lock), but still limited by segment count

### Synchronized Wrappers
`Collections.synchronizedList()`, `synchronizedMap()` — single monitor lock on all operations. Poor concurrency scalability.

## 2.2 Java 8 Collection Revolution

### HashMap Treeification
Java 8 introduced **Red-Black Trees** for collision handling:

> "When a bucket contains more than 8 nodes AND capacity ≥ 64, HashMap converts the Linked List into a Red Black Tree... Search complexity improves from O(n) to O(log n)." 

**Treeification rules:**
- **TREEIFY_THRESHOLD = 8**: Convert linked list to tree
- **UNTREEIFY_THRESHOLD = 6**: Revert tree to linked list on removal
- **MIN_TREEIFY_CAPACITY = 64**: Don't treeify if table is too small; resize instead

**Why this matters:**
- Defends against **hash collision attacks** (e.g., malicious HTTP POST params)
- Maintains O(1) average case, O(log n) worst case
- Only pays tree overhead when actually needed

### ConcurrentHashMap Rewrite (Java 8)
Java 8 replaced segment locking with **fine-grained CAS + synchronized on first nodes**:

> "From Java 8 onwards, it uses CAS (Compare-And-Swap) for atomic updates. Fine-grained synchronization only when required. Node arrays and buckets, similar to HashMap." 

**Internal changes:**
- **No more segments**: Direct array of `Node<K,V>` like HashMap
- **CAS on empty slots**: Lock-free insertion into empty buckets
- **Synchronized on first node**: Only lock the specific bucket's head node
- **Forwarding nodes**: During resize, threads help migrate buckets (cooperative resizing)
- **Counter cells**: Striped `LongAdder`-style counter for `size()` to reduce contention

**Performance impact:**
- Higher concurrency: Threads rarely block each other
- `compute()`, `merge()`, `forEach()` parallel-friendly methods added

### Lambda-Friendly Default Methods
Java 8 added default methods to interfaces:
- `Iterable.forEach()`, `Collection.removeIf()`
- `Map.forEach()`, `Map.compute()`, `Map.merge()`, `Map.putIfAbsent()`
- These enable functional-style operations without breaking existing implementations

## 2.3 ArrayList vs LinkedList: Memory & Cache Deep Dive

**Memory layout:**
- **ArrayList**: Contiguous array. Object header (12B) + 4B per reference. Total ~4KB for 1000 elements. 
- **LinkedList**: Each node = object header (12B) + data reference + prev + next = ~24B per node. Total ~24KB for 1000 elements. 

**Cache locality:**
> "Pointer chasing hurts the performance of reading random values in a LinkedList... having a linked list with nodes randomly distributed in the memory is three times slower." 

**Real-world performance paradox:**
Despite O(1) insertion, `LinkedList` is often **slower than ArrayList** even for insertions because:
- Each node is a separate object allocation (GC pressure)
- Pointer chasing causes cache misses
- `ArrayList.add()` at end is amortized O(1) and cache-friendly

> "ArrayList outperforms LinkedList for all the operations but one... because this efficient algorithm is executed on hardware that makes pointer chasing very costly." 

**When to use LinkedList:** Only when you need **Deque** operations (add/remove at both ends) and even then, prefer `ArrayDeque` unless you need null elements.

# 3. Java Streams: Internals & Performance

## 3.1 Pre-Java 8: External Iteration

```java
// Imperative, external iteration
List<String> result = new ArrayList<>();
for (String s : list) {
    if (s.startsWith("A")) {
        result.add(s.toUpperCase());
    }
}
```
- **External iteration**: Caller controls the loop
- **Eager evaluation**: Every step executes immediately
- **Verbose**: Boilerplate for filtering, mapping, collecting

## 3.2 Java 8 Streams: Internal Iteration

### Stream Pipeline Architecture
A Stream pipeline has three components:
1. **Source**: Collection, array, generator function, I/O channel
2. **Intermediate Operations**: `filter`, `map`, `sorted`, `distinct` — **lazy**
3. **Terminal Operation**: `collect`, `reduce`, `forEach` — triggers execution

**Lazy evaluation example:**
```java
list.stream()
    .filter(s -> { System.out.println("filter: " + s); return s.startsWith("A"); })
    .map(s -> { System.out.println("map: " + s); return s.toUpperCase(); })
    .findFirst(); // Only processes elements until first match!
```

### Spliterator: The Secret Engine
`Spliterator` (Splittable Iterator) is the core abstraction:
- **`tryAdvance()`**: Process next element
- **`trySplit()`**: Divide data for parallel processing
- **`characteristics()`**: `ORDERED`, `SIZED`, `NONNULL`, `IMMUTABLE`, etc.

**Source splitting efficiency:**
- **ArrayList/arrays**: O(1) split via index range — excellent for parallel
- **LinkedList/Stream.iterate()**: O(n) split — terrible for parallel 
- **IntStream.range()**: Direct spliterator — optimal

### Stream Fusion & Short-Circuiting
The JVM optimizes pipelines via:
- **Fusion**: Multiple intermediate ops fused into a single pass (no intermediate collections)
- **Short-circuiting**: `findFirst`, `anyMatch`, `limit` can stop early
- **Stateless ops**: `filter`, `map` can be reordered/parallelized freely
- **Stateful ops**: `sorted`, `distinct` require buffering — expensive in parallel

## 3.3 Performance: Streams vs Loops

JMH benchmarks consistently show:

> "The classic for loop is significantly faster than the others for simple iteration... However, the real power of Streams isn't in simple iteration; it's in creating expressive data processing pipelines." 

**Benchmark results** (filter evens, square, sum 1M integers):
- **For-loop**: ~3.4 ms
- **Stream (sequential)**: ~12.2 ms 

**Why streams are slower for simple cases:**
1. **Object overhead**: Stream objects, `Spliterator`, lambda capture
2. **Virtual method calls**: Per-element polymorphic dispatch
3. **Boxing**: `Stream<Integer>` vs `IntStream` — critical difference
4. **Setup overhead**: Fixed cost amortizes over large datasets

**When streams win:**
- Complex pipelines with multiple operations (fusion benefits)
- Parallel streams on large, splittable data sources
- Readability/maintainability (often worth the 2-4x overhead)

## 3.4 Parallel Streams: Boon or Bane?

> "Converting a sequential stream into a parallel one resulted in worse performance... The overhead of managing threads, sources and results is a more expensive operation than doing the actual work." 

**Parallel stream pitfalls:**
1. **Wrong source**: `LinkedList`, `Stream.iterate()`, `Stream.of()` — poor splitting
2. **Too small data**: Splitting overhead dominates below ~10,000 elements
3. **Stateful ops**: `sorted()`, `distinct()` require coordination
4. **Boxing**: `Stream<Integer>` vs `IntStream` — boxing kills parallel gains
5. **Common pool starvation**: `ForkJoinPool.commonPool()` shared globally 
6. **Thread interference**: Wrong thread pool for I/O-bound tasks

**Best practices:**
- Use `IntStream`, `LongStream`, `DoubleStream` (primitives, no boxing)
- Ensure source is `SIZED` and `SUBSIZED` (arrays, `IntStream.range`)
- Call `.unordered()` if order doesn't matter (better parallel scaling)
- Use custom `ForkJoinPool` for I/O tasks: `pool.submit(() -> list.parallelStream().map(...).collect(...))`

# 4. System Design Interview POV: Tradeoffs

## 4.1 Threading Model Selection

| Scenario | Pre-Java 8 Approach | Java 8+ Approach | Tradeoff |
|----------|-------------------|------------------|----------|
| CPU-bound parallel computation | `ThreadPoolExecutor` + manual task splitting | `parallelStream()` or `CompletableFuture` | Java 8+ reduces boilerplate but hides pool tuning |
| Async I/O (HTTP, DB) | Blocking `Future.get()` in thread pool | `CompletableFuture` chains + custom executor | Java 8+ composable but risk of callback hell |
| High concurrency, shared state | `ConcurrentHashMap` (segments) | `ConcurrentHashMap` (CAS) | Java 8+ significantly better throughput |
| Event-driven pipeline | Custom observer pattern | `CompletableFuture` pipeline | Java 8+ standardizes but less flexible than Reactive Streams |

## 4.2 Collection Selection Matrix

| Requirement | Choice | Rationale |
|-------------|--------|-----------|
| Fast random access, cache-friendly | `ArrayList` | Contiguous memory, O(1) access, prefetcher-friendly |
| Frequent insert/delete at ends | `ArrayDeque` | Circular array, no node allocation, cache-friendly |
| Frequent insert/delete in middle | `LinkedList` (rarely) | O(1) if iterator positioned, but cache misses hurt |
| High-concurrency read-heavy | `ConcurrentHashMap` | CAS reads, no locking for gets |
| High-concurrency write-heavy | `ConcurrentHashMap` + `LongAdder` | Striped counters, cooperative resizing |
| Ordered map with range queries | `TreeMap` | Red-black tree, O(log n) operations |
| LRU cache | `LinkedHashMap` (accessOrder=true) | O(1) operations + doubly-linked list for eviction |

## 4.3 Stream vs Loop Decision Tree

```
Is the operation simple (single pass, no transformation)?
├── YES → Use for-loop (2-4x faster)
└── NO → Is data large (>100K) and CPU-bound?
    ├── YES → Use parallelStream() with primitive streams
    └── NO → Use sequential Stream (readability, fusion benefits)
```

# 5. Real-Time Design Scenarios

## Scenario 1: Real-Time Analytics Aggregation Pipeline

**Problem:** Build a system that ingests 100K events/second from IoT sensors, computes per-minute aggregations (avg, max, min), and serves sub-second queries.

### Design Decisions

**Threading Model:**
- **Ingestion layer**: Netty/event-loop (1 thread per core) for non-blocking I/O
- **Processing layer**: `ForkJoinPool` with custom parallelism = cores * 2 (some I/O wait)
- **Aggregation engine**: Ring buffer (Disruptor pattern) — single writer, batch consumers

**Collection Strategy:**
```java
// Per-minute window: ConcurrentHashMap for thread-safe sensor state
ConcurrentHashMap<String, SensorWindow> windows = new ConcurrentHashMap<>();

// Java 8 compute() for lock-free aggregation
windows.compute(sensorId, (id, window) -> {
    if (window == null) window = new SensorWindow();
    window.addReading(value);
    return window;
});
```

**Why `ConcurrentHashMap.compute()` (Java 8+)?**
- Pre-Java 8: `putIfAbsent` + `get` + `synchronized` block = multiple lock acquisitions
- Java 8: Single CAS or synchronized-on-node operation — atomic and faster

**Stream Usage:**
```java
// BAD: Parallel stream on small per-sensor dataset
sensorList.parallelStream().map(...); // Overhead >> benefit

// GOOD: Batch processing with IntStream primitives
IntStream.of(readings)
    .filter(r -> r > THRESHOLD)
    .summaryStatistics(); // Single-pass, no boxing
```

**Tradeoffs:**
- **Throughput vs Latency**: Ring buffer gives throughput but adds ~1ms latency
- **Memory vs Accuracy**: Tumbling windows (fixed) vs sliding windows (higher memory)
- **CPU vs Consistency**: Eventual consistency with `LongAdder` counters vs exact `AtomicLong`

## Scenario 2: E-Commerce Order Processing with Inventory

**Problem:** Process 10K orders/second. Each order must:
1. Check inventory (DB/cache lookup)
2. Reserve stock (atomic decrement)
3. Process payment (external API)
4. Emit notification

### Design Decisions

**Threading Model:**
- **Pre-Java 8 approach**: Fixed thread pool of 200 threads. Each thread blocks on DB + payment API. Risk: Thread exhaustion under load.
- **Java 8+ approach**: `CompletableFuture` pipeline with **custom executor** (not common pool!):

```java
ExecutorService dbExecutor = Executors.newFixedThreadPool(50);
ExecutorService paymentExecutor = Executors.newFixedThreadPool(100);

CompletableFuture.supplyAsync(() -> checkInventory(order), dbExecutor)
    .thenComposeAsync(inventory -> 
        inventory.isAvailable() 
            ? reserveStock(order).thenComposeAsync(reserved -> 
                processPayment(order), paymentExecutor)
            : CompletableFuture.completedFuture(OrderStatus.OUT_OF_STOCK),
        dbExecutor)
    .exceptionally(ex -> OrderStatus.FAILED);
```

**Why custom executors?**
> "API call blocks thread. ForkJoinPool gets exhausted. Performance degrades. Result: Thread starvation." 

**Collection Strategy:**
```java
// Inventory cache: ConcurrentHashMap with compute() for atomic reservation
ConcurrentHashMap<String, AtomicInteger> inventory = new ConcurrentHashMap<>();

// Java 8 merge() for atomic stock decrement
inventory.merge(productId, -quantity, Integer::sum);
```

**Stream Usage for Reporting:**
```java
// Daily sales report: parallel stream on large dataset
List<DailySales> report = orders.parallelStream()
    .filter(o -> o.getDate().equals(today))
    .collect(Collectors.groupingByConcurrent(
        Order::getCategory,
        Collectors.summingLong(Order::getAmount)
    ))
    .entrySet().parallelStream() // Note: second parallel stream needs care
    .map(e -> new DailySales(e.getKey(), e.getValue()))
    .collect(Collectors.toList());
```

**Tradeoffs:**
- **Async complexity**: `CompletableFuture` chains are hard to debug (broken stack traces). Consider Virtual Threads (Java 21+) for imperative async.
- **Inventory consistency**: `ConcurrentHashMap.merge()` is atomic for a single SKU, but distributed transactions across SKUs need Saga pattern.
- **Cache vs DB**: Local `ConcurrentHashMap` is fast but inconsistent across nodes. Use Redis + local cache with TTL for read-heavy inventory checks.
- **Backpressure**: `ThreadPoolExecutor` with bounded queue + `CallerRunsPolicy` prevents OOM under spike.

## Summary Cheat Sheet

| Aspect | Pre-Java 8 | Java 8+ | Interview Tip |
|--------|-----------|---------|---------------|
| **Threading** | `ThreadPoolExecutor`, blocking `Future` | `ForkJoinPool`, `CompletableFuture` | Never use common pool for I/O |
| **Collections** | Segment-locked `ConcurrentHashMap`, linked-list HashMap | CAS `ConcurrentHashMap`, treeified HashMap | Treeification defends against DoS |
| **Streams** | External iteration, loops | Internal iteration, lazy fusion | Use primitives; avoid parallel on small data |
| **Memory** | `LinkedList` for insertions | `ArrayList`/`ArrayDeque` almost always | Pointer chasing kills performance |
| **Design** | Thread-per-request | Async pipeline with backpressure | Custom executors, bounded queues |
